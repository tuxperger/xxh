# Цикл фичи в xxh

Запрос пользователя: `$ARGUMENTS`

**Правило проекта.** Любая фича — новая возможность, изменение поведения, новый
флаг, новый источник/транспорт — идёт через spec kit. Команды `/speckit-*` вызываешь
сам, через инструмент Skill, не дожидаясь, пока пользователь их наберёт. Код в
`crates/`, `bootstrap/`, `nix/`, `tests/`, `flake.nix` правится только под открытую
задачу из `tasks.md` активной фичи — иначе хук `spec-gate` запросит подтверждение.

Исключение — hotfix: исправление поведения, которое уже описано в существующей спеке
и просто не выполняется. Его делают без новой спеки, но говорят об этом вслух и
ссылаются на нарушенное требование (`specs/NNN-…/spec.md`, FR-NNN).

## Где что лежит

| Что | Где |
| --- | --- |
| Активная фича | `.specify/feature.json` → `.specify/scripts/xxh/feature.sh` |
| Все фичи и их стадии | `specs/ROADMAP.md` (генерируется, руками не править) |
| Конституция (принципы I–XI) | `.specify/memory/constitution.md` |
| Хуки этапов spec kit | `.specify/extensions.yml` |
| Гейты качества | `.specify/scripts/xxh/gates.sh`, скилл `xxh-quality-gates` |

## Порядок

1. **Выбрать фичу.**
   - Новая → `/speckit-specify <описание>`. Каталог `specs/NNN-имя/` и запись в
     `feature.json` создаёт сама команда.
   - Уже заведённая в роадмапе → `.specify/scripts/xxh/feature.sh use NNN`.
     Дальше команды работают с ней.
2. **`/speckit-specify`** — что и зачем, без «как». В шапке спеки обязательны
   `**Priority**` и `**Summary**` (их читает роадмап). Не больше трёх
   `[NEEDS CLARIFICATION]`.
3. **`/speckit-clarify`** — только если в спеке остались маркеры или решение меняет
   объём/безопасность. Вопросы, на которые отвечает конституция или существующий
   код, закрывай сам и записывай в Assumptions; пользователя спрашивай только о
   том, что действительно его выбор.
4. **`/speckit-plan`** — research.md, data-model.md, contracts/, quickstart.md.
   Раздел Constitution Check заполняется по существу: для каждого принципа — как
   фича его соблюдает. Нарушение без обоснования — стоп.
5. **`/speckit-checklist`** — по одному чек-листу на зону риска фичи (безопасность,
   транспорт, плагины, nix…). Для фич, задевающих принципы I и V, обязателен.
6. **`/speckit-tasks`** — задачи по user stories; интеграционные тесты входят в
   задачи (Принцип VIII), а не откладываются «на потом».
7. **`/speckit-analyze`** — запускается хуком `after_tasks` автоматически. CRITICAL
   и HIGH находки исправляются в артефактах до реализации.
8. **`/speckit-implement`** — по задачам, отмечая `[X]` по мере выполнения. Перед
   ним — скилл `xxh-git` (ветка фичи), по ходу — `xxh-rust`, `xxh-integration-tests`,
   `xxh-nix`, `xxh-plugin-dev` по теме задачи.
9. **`xxh-quality-gates`** — хук `after_implement`, автоматически.
10. **`/speckit-converge`** — сверка кода со спекой; недостающее дописывается в
    `tasks.md` и доделывается.
11. В шапке спеки `**Status**: Implemented`, обновить README, если изменилось
    пользовательское поведение.

## Точки, где останавливаться

Между этапами не спрашивай «продолжать?» — иди дальше. Остановиться и показать
пользователю нужно, когда:

- спека содержит развилку, меняющую объём фичи, и разумного умолчания нет;
- план требует поправки конституции (отдельный шаг `/speckit-constitution`);
- реализация упёрлась в гейт, который не чинится в рамках задач фичи.

## Мелкие правила

- Одна фича — один каталог. Не дописывай новую возможность в чужую спеку: заводи
  следующую NNN и ссылайся на прежнюю.
- Язык артефактов — русский, идентификаторы (`FR-001`, `SC-001`, `T001`, `US1`) —
  как в шаблонах.
- Нумерация требований в новой спеке начинается с FR-001; на требования других
  фич ссылайся с номером фичи: `001 §FR-016`.
- Идеи на будущее не теряй: заведи спеку стадии `spec` через `/speckit-specify`
  (скилл `xxh-roadmap`), а не оставляй TODO в коде.
