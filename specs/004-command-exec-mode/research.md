# Research: Выполнение одной команды в своём окружении

## R1. Как дать команде stdio клиента

- **Decision**: новый метод `Transport::exec_stream(&mut self, cmd) -> Result<i32>`:
  команда без PTY, её stdin/stdout/stderr связаны с потоками процесса клиента,
  результат — код возврата.
  - russh: session-канал + `exec`; задача-форвардер читает stdin клиента и по EOF
    закрывает запись канала; `Data` → stdout, `ExtendedData` → stderr.
  - system ssh: `ssh -T <alias> -- <cmd>` с унаследованными дескрипторами.
  - container: `<runtime> exec -i <ref> sh -c <cmd>` с унаследованными дескрипторами.
- **Rationale**: существующий `exec` буферизует весь вывод и не имеет stdin;
  `open_pty` смешивает потоки и портит байты (CRLF). Унаследованные дескрипторы у
  CLI-бэкендов дают побайтную точность бесплатно.
- **Alternatives**: расширить `exec` параметрами — ломает все вызовы; использовать
  PTY — нарушает SC-001 и раздельность потоков.

## R2. Список аргументов против строки

- **Decision**: аргументы после `--` экранируются по одному (одинарные кавычки) и
  исполняются как `exec a1 a2 …` после prelude — без интерпретации шеллом.
  `-c <строка>` исполняется как `<шелл пользователя> -c '<строка>'`.
- **Rationale**: FR-006 требует точной передачи аргументов (в отличие от `ssh`,
  который склеивает и переинтерпретирует); конвейеры и алиасы нужны тоже — для них
  явный флаг, как `sh -c`.

## R3. Прерывание

- **Decision**: внутренний `sh -c` перед `exec` записывает свой pid в
  `<root>/sessions/<sid>.cmd` (после `exec` это pid самой команды). `Session::run_exec`
  ждёт либо завершения `exec_stream`, либо SIGINT/SIGTERM клиента; по сигналу
  отменяет поток и выполняет через обычный `exec`: `kill -TERM <pid>` и ожидание
  исчезновения маркера сессии (до 5 с). Возвращает 128 + номер сигнала.
- **Rationale**: bootstrap запускает команду как дочерний процесс и ставит trap
  очистки на EXIT — когда команда умирает, bootstrap завершается и чистит за собой.
  Сам bootstrap убивать бесполезно: шелл откладывает trap до завершения дочернего
  процесса. Решение не зависит от транспорта (Принцип III): `docker exec -i` без TTY
  сигнал внутрь контейнера не передаёт, russh без PTY — тоже.
- **Alternatives**: SSH-запрос `signal` — только для одного бэкенда и не везде
  поддержан; фоновый запуск команды в bootstrap — фоновые задачи теряют stdin.
- Файл `.cmd` — обычный маркер с pid: существующий reconcile уберёт его, если
  очистка не отработала; `xxh_cleanup` удаляет его явно.

## R4. Коды возврата

- **Decision**: код команды передаётся как есть (0–255). Команда убита сигналом →
  128 + номер; код неизвестен → 255. Ошибки xxh — прежние 10/20/30/40 и 2 для
  ошибок использования, всегда с сообщением `xxh: <класс>: …`.
- **Rationale**: соглашение шеллов; сейчас отрицательный код обрезается до 0, что для
  режима команды недопустимо.

## R5. Интерактивные запросы

- **Decision**: `read_secret` возвращает ошибку аутентификации, если stdin не
  терминал; system ssh сам читает пароль с `/dev/tty`. Сообщения об этапах в режиме
  команды идут в stderr только при `-v`.
- **Rationale**: FR-009 — иначе первая строка переданных по конвейеру данных была бы
  прочитана как пароль.

## R6. Терминал по запросу

- **Decision**: `-t/--tty` запускает команду через существующий `open_pty`.
- **Rationale**: FR-008; код уже есть, меняется только запускаемая строка.

## R7. Тесты

- **Decision**: три интеграционных файла запускают собранный бинарь
  (`CARGO_BIN_EXE_xxh`) с `HOME` фикстуры — проверяется настоящий stdio процесса.
