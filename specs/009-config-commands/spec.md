# Feature Specification: Команды работы с конфигурацией

**Feature Branch**: `009-config-commands`

**Created**: 2026-10-01

**Status**: Implemented

**Priority**: P2

**Summary**: `xxh config init|validate|edit|set` — создать, проверить и поправить конфиг без чтения документации по формату

**Input**: User description: "`xxh config validate|edit|init`: сейчас есть только `path` и `show`; схема для валидации уже существует."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Проверить конфиг (Priority: P1)

Пользователь отредактировал конфиг вручную или сгенерировал его и хочет убедиться, что
в нём нет ошибок, не подключаясь никуда.

**Why this priority**: ошибка в конфиге сегодня обнаруживается только при попытке
входа; проверка нужна и в CI для декларативных конфигураций.

**Independent Test**: `xxh config validate` на корректном файле — код 0; на файле с
неизвестным ключом или неверным значением — код класса «конфигурация» и указание места.

**Acceptance Scenarios**:

1. **Given** корректный конфиг, **When** выполняется `xxh config validate`, **Then**
   код возврата нулевой.
2. **Given** конфиг с недопустимым значением, **When** выполняется проверка, **Then**
   ошибка называет ключ, недопустимое значение, допустимые значения и место в файле.
3. **Given** конфиг с неизвестным ключом (опечатка), **When** выполняется проверка,
   **Then** пользователь получает предупреждение с ближайшим известным ключом.
4. **Given** путь к произвольному файлу, **When** он передан команде, **Then**
   проверяется этот файл, а не файл по умолчанию.

---

### User Story 2 - Создать начальный конфиг (Priority: P2)

Новый пользователь получает прокомментированный конфиг со значениями по умолчанию, от
которого можно отталкиваться.

**Why this priority**: снижает порог входа, но инструмент работает и без конфига.

**Independent Test**: `xxh config init` на клиенте без конфига создаёт файл, который
проходит проверку и даёт то же эффективное поведение, что и отсутствие файла.

**Acceptance Scenarios**:

1. **Given** конфига нет, **When** выполняется `xxh config init`, **Then** создаётся
   файл с прокомментированными значениями по умолчанию.
2. **Given** конфиг уже существует, **When** выполняется `init`, **Then** файл не
   перезаписывается без явного согласия.

---

### User Story 3 - Изменить значение из командной строки (Priority: P3)

Пользователь меняет одно значение — глобально или для хоста — не открывая редактор, либо
открывает конфиг в своём редакторе с проверкой после сохранения.

**Why this priority**: удобство; ручное редактирование остаётся доступным.

**Independent Test**: `xxh config set hosts.web.default_shell fish`, затем
`xxh config show --host web` показывает новое значение.

**Acceptance Scenarios**:

1. **Given** существующий конфиг, **When** пользователь задаёт значение ключа командой,
   **Then** значение изменено, остальное содержимое файла сохранено.
2. **Given** недопустимое значение, **When** пользователь пытается его задать, **Then**
   файл не меняется.
3. **Given** `xxh config edit`, **When** пользователь сохраняет файл с ошибкой, **Then**
   ему показана ошибка и предложено вернуться к редактированию.

---

### Edge Cases

- Конфиг управляется декларативно (сгенерирован и доступен только для чтения) —
  изменяющие команды отказывают с объяснением.
- Комментарии и порядок ключей в файле при изменении значения сохраняются.
- Редактор не задан — сообщается, как его указать.
- Каталог конфигурации отсутствует — создаётся командой `init`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять команду проверки конфига по умолчанию или
  указанного файла без подключения к целям.
- **FR-002**: Ошибки проверки MUST указывать ключ, место в файле, недопустимое значение
  и допустимые значения.
- **FR-003**: Неизвестные ключи MUST сообщаться как предупреждения с подсказкой
  ближайшего известного ключа.
- **FR-004**: Система MUST предоставлять команду создания начального конфига, не
  перезаписывающую существующий файл без явного согласия.
- **FR-005**: Созданный начальный конфиг MUST давать то же поведение, что и отсутствие
  конфига.
- **FR-006**: Система MUST предоставлять команды чтения, изменения и сброса отдельного значения,
  глобального и для конкретного хоста.
- **FR-007**: Изменение значения MUST сохранять комментарии и прочее содержимое файла и
  MUST отклонять недопустимые значения, не меняя файл.
- **FR-008**: Система MUST предоставлять команду открытия конфига в редакторе
  пользователя с проверкой результата.
- **FR-009**: Изменяющие команды MUST отказывать с объяснением, если файл недоступен для
  записи (в том числе управляется декларативно).
- **FR-010**: Все ошибки этих команд MUST относиться к классу «конфигурация».

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Любая ошибка конфига, которая помешает входу, обнаруживается проверкой без
  подключения.
- **SC-002**: По сообщению проверки пользователь исправляет ошибку с первой попытки, не
  обращаясь к документации.
- **SC-003**: Изменение значения командой не теряет ни одного комментария файла.
- **SC-004**: Проверка пригодна для автоматизации: результат определяется кодом возврата.

## Assumptions

- Канонический формат и единственный файл конфигурации остаются прежними (Принцип XI);
  команды — способ его порождения и проверки, а не новая система настроек.
- Проверка конфига как часть общей диагностики — фича 006.
- «Явное согласие» на перезапись — отдельный флаг команды; интерактивных вопросов,
  кроме «править снова?» в `edit`, нет.
- Предупреждения (неизвестные ключи) не меняют код возврата; для автоматизации есть
  строгий режим, в котором они считаются ошибкой.
- «Управляется декларативно» распознаётся по тому, что файл — символическая ссылка
  или недоступен для записи.
- Существующие команды, меняющие конфиг (включение и выключение плагинов), подчиняются
  тем же правилам сохранения содержимого и отказа.
