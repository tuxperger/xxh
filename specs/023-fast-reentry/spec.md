# Feature Specification: Быстрый повторный вход без повторной упаковки и пересылки

**Feature Branch**: `023-fast-reentry`

**Created**: 2026-10-01

**Status**: Implemented

**Priority**: P1

**Summary**: Повторный вход и запуск команды в сохранённом окружении занимают доли секунды: неизменившееся не упаковывается и не пересылается

**Input**: User description: "При реализации 004 замер показал: `xxh <цель> --keep -- true` в уже развёрнутое окружение занимает ~2,8 с на локальном контейнере (голый exec — 24 мс). Клиент при каждом входе заново упаковывает все компоненты (шелл, плагины) ещё до сверки с целью, а сгенерированные компоненты (env, terminfo) каждый раз получают новый адрес и пересылаются заново даже при `--keep`. Это нарушает 001 §FR-013 и Принцип VI и не даёт выполнить 004 SC-004."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Мгновенный повторный вход (Priority: P1)

Пользователь работает с хостом весь день с `--keep`: входит, выходит, запускает
отдельные команды из скриптов. Каждый следующий вход или запуск занимает столько же,
сколько установка соединения, — окружение уже на месте и не изменилось.

**Why this priority**: задержка в секунды на каждый запуск делает режим одной команды
(004) непригодным для циклов и скриптов и заметна при обычном входе.

**Independent Test**: дважды подряд выполнить команду в сохранённое окружение; второй
запуск ничего не передаёт на цель и укладывается во время подключения плюс секунда.

**Acceptance Scenarios**:

1. **Given** окружение сохранено на цели и не менялось на клиенте, **When** пользователь
   входит повторно, **Then** на цель не передаётся ни один компонент.
2. **Given** те же условия, **When** пользователь запускает команду, **Then** время от
   запуска до начала выполнения команды не превышает времени подключения плюс секунды.
3. **Given** на клиенте изменён один плагин, **When** пользователь входит, **Then**
   передаётся только он.

---

### User Story 2 - Предсказуемые адреса компонентов (Priority: P2)

Один и тот же набор файлов всегда даёт один и тот же адрес компонента — на любом
клиенте и при любом запуске, — так что сохранённое окружение переиспользуется и между
машинами пользователя.

**Why this priority**: основа для первой истории и для проверки целостности (014) и
lock-файла (013).

**Independent Test**: упаковать один и тот же каталог дважды с разными временами
изменения файлов — адрес одинаков.

**Acceptance Scenarios**:

1. **Given** каталог компонента с неизменным содержимым, **When** он готовится к
   доставке в разное время, **Then** адрес компонента совпадает.
2. **Given** служебные компоненты, которые клиент генерирует сам, **When** они
   готовятся повторно без изменения содержимого, **Then** их адрес не меняется.

---

### Edge Cases

- Файл изменён без изменения размера и времени — изменение всё равно обнаруживается.
- Локальный кеш подготовленных компонентов повреждён или удалён — компоненты
  готовятся заново, вход не ломается.
- Изменились только права доступа файла — это считается изменением компонента.
- Цель потеряла часть сохранённого окружения — недостающее доставляется.
- Первый вход (ничего не сохранено) не замедляется.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Адрес компонента MUST определяться только его содержимым (имена, данные,
  права доступа файлов) и MUST NOT зависеть от времени подготовки, времён изменения
  файлов и расположения на клиенте.
- **FR-002**: Компонент, уже присутствующий на цели, MUST NOT передаваться повторно —
  включая компоненты, которые клиент генерирует сам.
- **FR-003**: Клиент MUST NOT заново готовить к передаче компонент, содержимое которого
  не изменилось с прошлой подготовки.
- **FR-004**: Изменение содержимого компонента MUST обнаруживаться при следующем входе
  в 100% случаев.
- **FR-005**: Повреждение или отсутствие клиентского кеша подготовленных компонентов
  MUST приводить к повторной подготовке, а не к ошибке.
- **FR-006**: Первый вход MUST занимать не больше времени, чем до этой фичи.
- **FR-007**: Поведение MUST быть одинаковым для интерактивного входа и запуска одной
  команды, для всех транспортов.
- **FR-008**: В подробном режиме пользователь MUST видеть, сколько компонентов
  передано и сколько переиспользовано.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Повторный вход в неизменённое сохранённое окружение не передаёт на цель
  ни одного компонента.
- **SC-002**: Запуск команды в сохранённое окружение на локальной цели начинается не
  позже чем через одну секунду после установки соединения (сейчас — около трёх).
- **SC-003**: Один и тот же набор файлов даёт один и тот же адрес компонента при
  любом числе повторений.
- **SC-004**: Время первого входа не увеличилось.

## Assumptions

- Исправляет фактическое несоответствие 001 §FR-013 («передаётся только
  изменившееся») и закрывает 004 SC-004, который на момент реализации 004 не
  выполняется из-за этой причины.
- Протокол доставки и раскладка на цели не меняются; адреса существующих сохранённых
  окружений изменятся один раз — старые компоненты будут доставлены заново.
- Согласуется с 014 (целостность сохранённого окружения) и 013 (lock-файл), которые
  опираются на стабильные адреса.
