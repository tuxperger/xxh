# Feature Specification: Прогресс доставки окружения

**Feature Branch**: `015-delivery-progress`

**Created**: 2026-10-01

**Status**: Draft

**Priority**: P3

**Summary**: Во время доставки окружения видно, сколько передано, с какой скоростью и сколько осталось

**Input**: User description: "Прогресс доставки: байты и скорость при передаче компонентов; на медленном канале шелл с плагинами едет заметно долго, а пользователь видит только строку этапа."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Понятно, что происходит (Priority: P1)

Пользователь входит на хост по медленному каналу. Вместо неподвижной строки он видит,
какой компонент передаётся, сколько уже передано и сколько осталось, и понимает, что
инструмент не завис.

**Why this priority**: первая доставка шелла может занимать десятки секунд; без
обратной связи пользователи прерывают её.

**Independent Test**: при ограниченной скорости канала во время доставки отображаются
растущие показатели; по завершении — итог.

**Acceptance Scenarios**:

1. **Given** интерактивный терминал и доставка дольше секунды, **When** идёт передача,
   **Then** отображаются текущий компонент, переданный объём, общий объём и скорость.
2. **Given** доставка завершена, **When** открывается сессия, **Then** индикатор убран
   и не засоряет экран; при подробном режиме остаётся итоговая строка.
3. **Given** все компоненты переиспользованы, **When** пользователь входит, **Then**
   индикатор не появляется.

---

### User Story 2 - Не мешать автоматизации (Priority: P2)

Когда вывод перенаправлен или идёт выполнение одной команды, индикатор не выводит
управляющих последовательностей и не попадает в стандартный вывод.

**Why this priority**: иначе индикатор ломает журналы CI и конвейеры.

**Independent Test**: при перенаправлении потока ошибок в файл в нём нет управляющих
последовательностей, только итоговые строки.

**Acceptance Scenarios**:

1. **Given** поток вывода не является терминалом, **When** идёт доставка, **Then**
   выводятся только простые строки этапов без перерисовки.
2. **Given** пользователь отключил индикатор флагом или настройкой, **When** идёт
   доставка, **Then** индикатор не показывается.

---

### Edge Cases

- Узкий терминал — индикатор умещается в ширину без переноса строк.
- Изменение размера окна во время доставки.
- Общий объём заранее неизвестен — показываются переданный объём и скорость.
- Быстрая доставка (меньше секунды) — индикатор не мелькает.
- Прерывание пользователем — строка индикатора очищена, терминал в исправном состоянии.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Во время доставки в интерактивном терминале система MUST показывать
  передаваемый компонент, переданный и общий объём и скорость.
- **FR-002**: Индикатор MUST выводиться только в поток диагностики и MUST NOT попадать
  в стандартный вывод.
- **FR-003**: Если поток диагностики не является терминалом, система MUST выводить
  только построчные сообщения без управляющих последовательностей.
- **FR-004**: Индикатор MUST NOT появляться для доставки короче заданного порога и при
  полном переиспользовании компонентов.
- **FR-005**: Пользователь MUST иметь возможность отключить индикатор.
- **FR-006**: По завершении или прерывании доставки терминал MUST оставаться в
  исправном состоянии.
- **FR-007**: Индикатор MUST работать одинаково для всех транспортов.
- **FR-008**: Отображение прогресса MUST NOT замедлять доставку заметным образом.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При доставке дольше одной секунды пользователь видит обновление
  показателей не реже двух раз в секунду.
- **SC-002**: В перенаправленном выводе нет ни одной управляющей последовательности.
- **SC-003**: Время доставки с индикатором отличается от времени без него не более чем
  на 2%.

## Assumptions

- Опирается на существующий механизм сообщений об этапах сессии (001 §FR-025).
- Оценка оставшегося времени — желательна, но не обязательна.
