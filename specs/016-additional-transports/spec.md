# Feature Specification: Транспорт Kubernetes — свой шелл в поде

**Feature Branch**: `016-additional-transports`

**Created**: 2026-10-01

**Status**: Draft

**Priority**: P2

**Summary**: `xxh k8s:[ns/]pod[:container]` — своё окружение в поде Kubernetes той же командой и с теми же гарантиями, что у docker-контейнеров

**Input**: User description: "Новые транспорты: `kubectl exec` (`k8s:ns/pod`) и nerdctl уже упомянуты в коде как будущие; туда же ложатся systemd-nspawn/machinectl, lxc/incus, WSL и `local:` для проверки окружения без сети." Уточнение при взятии в работу (2026-10-14): «оставь только k8s и докер» — docker уже поддержан фичей 002, поэтому объём фичи — Kubernetes с паритетом docker-транспорту; локальная цель и прочие рантаймы вынесены в фичу 025.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Под Kubernetes со своим окружением (Priority: P1)

Пользователь отлаживает сервис в кластере. Одной командой он входит в под со своим
шеллом и инструментами — без sshd в поде и без изменения образа; после выхода под чист.

**Why this priority**: самый востребованный класс целей после SSH и локальных
контейнеров; минимальные образы в кластерах — именно тот случай, где своё окружение
ценнее всего.

**Independent Test**: войти в под в тестовом кластере, выполнить команду в доставленном
окружении, выйти, убедиться в чистоте пода.

**Acceptance Scenarios**:

1. **Given** запущенный под и доступ пользователя к кластеру, **When** пользователь
   выполняет `xxh k8s:<пространство>/<под>`, **Then** он получает сессию своего шелла в
   поде.
2. **Given** под с несколькими контейнерами, **When** пользователь указывает контейнер,
   **Then** сессия открывается в нём; без указания — в контейнере по умолчанию с
   сообщением, какой выбран.
3. **Given** сессия завершена, **When** проверяется под, **Then** артефактов окружения
   нет.
4. **Given** у пользователя нет прав на вход в под, **When** он пытается войти,
   **Then** ошибка транспорта называет причину; учётные данные кластера не выводятся.
5. **Given** пространство имён не указано, **When** пользователь выполняет
   `xxh k8s:<под>`, **Then** используется пространство имён текущего контекста.

---

### User Story 2 - Те же возможности, что у docker-цели (Priority: P2)

Всё, что работает для `docker:`-цели, работает и для пода: выполнение одной команды
(`xxh k8s:… -- cmd`), `-t`, `--keep`, `xxh status`/`xxh clean`, `xxh doctor`,
переменные окружения `-e`, плагины и личные файлы.

**Why this priority**: пользователь не должен помнить, какие возможности есть у какого
транспорта (Принцип III).

**Independent Test**: команда в окружении пода возвращает свой код возврата и
разделённые stdout/stderr; `--keep` + `xxh status` + `xxh clean` на поде.

**Acceptance Scenarios**:

1. **Given** запущенный под, **When** пользователь выполняет `xxh k8s:<под> -- cmd`,
   **Then** код возврата равен коду `cmd`, потоки не смешаны.
2. **Given** окружение сохранено с `--keep`, **When** выполнены `xxh status k8s:<под>` и
   `xxh clean k8s:<под>`, **Then** первое показывает окружение, второе его удаляет.
3. **Given** контекст кластера, отличный от текущего, **When** пользователь передаёт
   `--kube-context <имя>`, **Then** сессия открывается в поде этого контекста.

---

### Edge Cases

- Под перезапущен или удалён во время сессии — ошибка транспорта, без зависания.
- В контейнере пода нет `sh` — явная ошибка доставки (контейнеры без шелла — фича 022).
- Под не в фазе `Running` или указанного контейнера в нём нет — ошибка транспорта до
  доставки, с перечнем контейнеров пода.
- Нет `kubectl` или кластер недоступен — ошибка транспорта только для `k8s:`-целей;
  SSH и docker работают как прежде.
- Неизвестный префикс цели — ошибка использования с перечнем поддерживаемых.
- Опции, применимые только к другому семейству (`-i`, `-A`, `--transport`,
  `--runtime`, `-l/--user`), отклоняются для `k8s:` до подключения; `--kube-context`
  отклоняется для не-k8s целей.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST поддерживать адресацию пода Kubernetes с указанием
  пространства имён (опционально), пода, контейнера (опционально) и контекста
  (опционально).
- **FR-002**: Без указания контейнера система MUST выбирать контейнер по умолчанию
  (аннотация `kubectl.kubernetes.io/default-container`, иначе первый) и сообщать,
  какой выбран.
- **FR-003**: Для пода MUST действовать единая семантика: определение платформы,
  доставка, кеширование, очистка, плагины, выполнение одной команды и флаги сессии —
  как у docker-цели.
- **FR-004**: Образы, манифесты и спецификации подов MUST NOT модифицироваться;
  единственный канал данных — `exec` в контейнер пода.
- **FR-005**: Аутентификация MUST опираться на уже имеющийся у пользователя доступ к
  кластеру (kubeconfig); система MUST NOT вводить собственные учётные данные и MUST NOT
  выводить или журналировать адрес API-сервера, токены и сырые ошибки `kubectl`.
- **FR-006**: Отсутствие `kubectl` или недоступность кластера MUST отключать только
  транспорт Kubernetes с понятным сообщением.
- **FR-007**: Добавление транспорта MUST NOT требовать изменений в логике
  развёртывания, плагинов и очистки (`xxh-core`).
- **FR-008**: Опции, специфичные для одного семейства целей, MUST отклоняться для
  других до подключения.
- **FR-009**: Транспорт MUST быть покрыт интеграционным сценарием против реального
  кластера с проверкой чистоты пода; без доступного кластера сценарий пропускается с
  сообщением.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь входит в под кластера со своим окружением одной командой, без
  подготовки пода.
- **SC-002**: После выхода под чист в 100% сценариев интеграционного набора, спецификация
  пода не изменена.
- **SC-003**: Набор возможностей сессии в поде совпадает с docker-целью (проверяется
  тем же сценарием: вход, команда, код возврата, чистота).

## Assumptions

- Продолжение фичи 002: под — третье семейство целей за существующим интерфейсом
  транспорта (Принцип III); бэкенд — CLI `kubectl`, как docker-бэкенд — CLI `docker`.
- Создание и запуск подов — вне рамок; под уже запущен.
- `kubectl exec` не умеет менять пользователя, поэтому `-l/--user` для `k8s:`
  отклоняется (FR-008), а не игнорируется.
- Автодополнение имён подов не делается: оно требует обращения к API кластера, а
  автодополнение не ходит в сеть (007 C-K9). Префикс `k8s:` дополняется.
- Пользовательский конфиг не получает новых ключей: контекст задаётся флагом
  `--kube-context` или текущим контекстом kubeconfig.
- Локальная цель `local:` и рантаймы nerdctl, incus/lxc, systemd-nspawn, WSL — фича 025.
