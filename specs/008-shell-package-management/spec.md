# Feature Specification: Управление пакетами шеллов из CLI

**Feature Branch**: `008-shell-package-management`

**Created**: 2026-10-01

**Status**: Draft

**Priority**: P1

**Summary**: `xxh shell add|list|fetch|remove` — установить шелл и его сборки под нужные платформы без ручных скриптов

**Input**: User description: "`xxh shell list|add|fetch`: шеллы ищутся в ~/.local/share/xxh/shells, а сборки под платформы добываются внешним fetch.sh. Управление из CLI, как у `plugin`, убирает ручной шаг."

## Clarifications

### Session 2026-10-01

- Q: Как xxh добывает сборки шелла под платформу? → A: декларативно (решение пользователя): манифест пакета описывает сборки — для каждой платформы адрес архива и его контрольную сумму SHA-256; xxh сам скачивает архив, проверяет сумму до распаковки, распаковывает во временный каталог, добавляет общие файлы пакета (`overlay/`), при необходимости запускает изолированный хук пакета `post_fetch` и только затем атомарно делает сборку видимой.
- Q: Куда устанавливаются пакеты шеллов? → A: в существующий путь поиска шеллов (`~/.local/share/xxh/shells/<шелл>/`, первый каталог `XXH_SHELLS_DIR`, если он задан): дерево пакета, его сборки в `dist/` и запись об источнике и загруженных сборках. Пакет, подключённый туда вручную (каталог или ссылка без записи об источнике), показывается как «подключён вручную»: `fetch` для него работает, `update` — нет, `remove` удаляет только ссылку, но не каталог, на который она указывает.
- Q: Какие сборки ставит `xxh shell add` по умолчанию? → A: все объявленные сборки для ОС, которые xxh поддерживает как цели (сейчас Linux); `--platform <ос-арх>` (повторяемый) задаёт набор явно, `--no-builds` — без сборок.
- Q: Чем скачиваются сборки? → A: внешней программой `curl` на клиенте (как `git` для git-источника); адреса `https://` и `file://`. Нет `curl` — ошибка класса «шелл» с указанием, что установить.
- Q: Как называется файл манифеста пакета шелла? → A: `plugin.toml`, как у любого пакета; `manifest.toml` существующих пакетов шеллов принимается тоже.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Установить шелл одной командой (Priority: P1)

Новый пользователь хочет свой zsh на удалённых хостах. Он выполняет одну команду — и
пакет шелла установлен вместе со сборками под нужные платформы; следующий вход даёт
этот шелл.

**Why this priority**: сегодня первый запуск требует вручную разложить пакет и
выполнить его скрипт загрузки; это главный барьер входа.

**Independent Test**: на чистом клиенте установить пакет шелла командой, войти на хост,
где этого шелла нет, и получить его.

**Acceptance Scenarios**:

1. **Given** клиент без пакетов шеллов, **When** пользователь выполняет
   `xxh shell add <источник>`, **Then** пакет установлен и готов к использованию.
2. **Given** установленный пакет шелла, **When** пользователь входит на хост, где
   этого шелла нет, **Then** он получает сессию этого шелла.
3. **Given** установленный пакет, **When** пользователь выполняет `xxh shell remove`,
   **Then** пакет и его сборки удалены с клиента.

---

### User Story 2 - Видеть, под какие платформы есть сборки (Priority: P2)

Пользователь видит список установленных шеллов и для каждого — под какие платформы
есть готовые сборки, а под какие нет.

**Why this priority**: отсутствие сборки под платформу цели — самая частая причина
неудачного входа, и сейчас она невидима.

**Independent Test**: `xxh shell list` показывает шелл и перечень платформ со статусом.

**Acceptance Scenarios**:

1. **Given** установленные пакеты, **When** выполняется `xxh shell list`, **Then** для
   каждого показаны версия, источник и платформы с готовыми сборками.
2. **Given** пакет без сборки под платформу, **When** пользователь входит на цель этой
   платформы, **Then** сообщение об ошибке называет команду, которая добудет сборку.

---

### User Story 3 - Дозагрузить сборку под платформу (Priority: P2)

Пользователь впервые идёт на хост с другой архитектурой и дозагружает сборку шелла под
неё — заранее или по подсказке.

**Why this priority**: держать на клиенте сборки под все платформы избыточно;
дозагрузка по мере надобности экономит место и время.

**Independent Test**: `xxh shell fetch <шелл> --platform <платформа>` добавляет сборку;
`list` это отражает.

**Acceptance Scenarios**:

1. **Given** пакет без сборки под платформу, **When** пользователь запрашивает её
   загрузку, **Then** сборка появляется, проверена на целостность и готова к доставке.
2. **Given** сборка уже есть, **When** запрос повторяется, **Then** повторной загрузки
   нет.
3. **Given** сборки под запрошенную платформу не существует, **When** выполняется
   запрос, **Then** ошибка перечисляет доступные платформы.

---

### Edge Cases

- Загрузка прервана — частичная сборка не считается установленной.
- Целостность загруженной сборки не подтверждена — сборка отклоняется.
- Два пакета предоставляют один и тот же шелл — конфликт сообщается явно.
- Нет сети — уже установленные сборки продолжают работать.
- Удаляется шелл, указанный в конфиге как шелл по умолчанию, — предупреждение.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять команды установки, удаления, обновления и
  перечисления пакетов шеллов.
- **FR-002**: Установка пакета шелла MUST поддерживать те же источники, что и установка
  плагинов.
- **FR-003**: Система MUST показывать для каждого пакета платформы, под которые есть
  готовые сборки.
- **FR-004**: Система MUST уметь загрузить сборку под указанную платформу без ручного
  запуска скриптов пакета.
- **FR-005**: Загруженная сборка MUST проверяться на целостность до использования.
- **FR-006**: Прерванная или неподтверждённая загрузка MUST NOT оставлять сборку,
  считающуюся установленной.
- **FR-007**: При входе на цель, под платформу которой нет сборки, сообщение об ошибке
  MUST называть команду, которая её добудет.
- **FR-008**: Ядро MUST NOT содержать зашитого списка шеллов: набор доступных шеллов
  определяется установленными пакетами.
- **FR-009**: Конфликт двух пакетов, предоставляющих один шелл, MUST сообщаться явно.
- **FR-010**: Ошибки управления пакетами шеллов MUST относиться к классу ошибок «шелл».

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Новый пользователь получает свой шелл на удалённом хосте не более чем за
  две команды после установки xxh.
- **SC-002**: Ни один шаг установки шелла не требует ручного копирования файлов или
  запуска сторонних скриптов.
- **SC-003**: Причина «нет сборки под платформу» видна пользователю и устранима одной
  командой в 100% случаев.
- **SC-004**: Повреждённая сборка никогда не доставляется на цель.

## Assumptions

- Пакеты шеллов остаются обычными пакетами системы плагинов (Принцип IV); команда —
  специализированный вид поверх неё, а не отдельный механизм.
- Автоматическая дозагрузка сборки в момент входа без запроса пользователя — вне
  рамок: загрузка из сети остаётся явным действием.
- Диагностика отсутствующих сборок до входа — фича 006.
