# Feature Specification: Диагностика клиента и цели до входа

**Feature Branch**: `006-doctor-preflight`

**Created**: 2026-10-01

**Status**: Implemented

**Priority**: P1

**Summary**: `xxh doctor [цель]` заранее сообщает, что помешает входу: нет пакета шелла под платформу, не хватает утилит или места

**Input**: User description: "`xxh doctor [host]` — проверка без доставки: платформа цели, наличие tar/gzip/zstd, свободное место, есть ли пакет шелла под эту платформу. Сейчас отсутствие payload под платформу пишется только в debug-лог и пользователь его не видит."

## Clarifications

### Session 2026-10-01

- Q: Какой код возврата у диагностики? → A: `0` — всё пройдено или есть только предупреждения; `1` — хотя бы одна проверка провалена; цель недостижима — `10` (класс транспорта), при этом проверки клиента всё равно выводятся.
- Q: Какие утилиты цели обязательны, а какие желательны? → A: обязательны `sh`, `cat`, `mkdir`, `chmod`, `tar`, `gzip` (контракт хоста); `zstd` (быстрее доставка), `du` (объём в `xxh status`) и `df` (проверка места) — желательны: их отсутствие — предупреждение.
- Q: Как проверяется место без записи на цель? → A: свободное место — `df -Pk` для каталога, куда лёг бы вход; требуемое — распакованный объём компонентов плана, которых на цели ещё нет; без `df` — предупреждение «место не проверено».
- Q: Что считается доступностью источников плагинов и рантаймов? → A: исполняемый `git` (и `nix`, если клиент собран с поддержкой Nix) и `docker`/`podman` в `PATH`; отсутствие — всегда предупреждение: установленные плагины уже лежат в реестре клиента, и для входа источник не нужен (он нужен для `xxh plugin add|update`).
- Q: Машиночитаемый формат? → A: `--json`, один объект в stdout: проверки клиента и, если задана цель, её платформа и проверки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Проверка цели без изменений на ней (Priority: P1)

Перед первым входом на новый хост пользователь хочет знать, заработает ли его окружение:
поддерживается ли платформа, есть ли всё необходимое, хватит ли места. Проверка ничего
не оставляет на цели.

**Why this priority**: сегодня причины неудачи видны только после попытки входа и
часто только в отладочном выводе.

**Independent Test**: `xxh doctor <цель>` на подходящем хосте — все проверки пройдены,
цель чиста; на хосте без нужной утилиты — проверка названа проваленной с объяснением.

**Acceptance Scenarios**:

1. **Given** достижимая цель, **When** пользователь выполняет `xxh doctor <цель>`,
   **Then** он видит определённую платформу и по каждой проверке — пройдена, с
   предупреждением или провалена, с причиной и действием.
2. **Given** для платформы цели нет пакета выбранного шелла, **When** выполняется
   диагностика, **Then** это названо явно, с указанием, какой пакет установить.
3. **Given** любой исход диагностики, **When** она завершена, **Then** на цель ничего
   не записано.
4. **Given** все проверки пройдены, **When** пользователь входит на цель, **Then** вход
   успешен.

---

### User Story 2 - Проверка клиента (Priority: P2)

Без указания цели пользователь проверяет собственную машину: корректен ли конфиг,
установлены ли включённые плагины, доступны ли источники плагинов и рантаймы
контейнеров.

**Why this priority**: значительная часть проблем — на клиенте, и их можно найти без
сети.

**Independent Test**: `xxh doctor` при включённом, но не установленном плагине сообщает
об этом и о способе исправить.

**Acceptance Scenarios**:

1. **Given** в конфиге включён неустановленный плагин, **When** выполняется
   `xxh doctor`, **Then** проблема названа с именем плагина.
2. **Given** опциональный источник плагинов недоступен на клиенте, **When** выполняется
   диагностика, **Then** это показано как предупреждение, а не как провал.
3. **Given** исправная конфигурация, **When** выполняется диагностика, **Then** код
   возврата нулевой.

---

### Edge Cases

- Цель недостижима — диагностика сообщает ошибку транспорта и всё же показывает
  результаты проверок клиента.
- Часть плагинов несовместима с платформой цели — перечислены как «будут пропущены».
- Места на цели меньше, чем нужно окружению, — провал с числами (нужно/доступно).
- Домашний каталог цели недоступен для записи — показано, в какой каталог ляжет
  окружение (вход использует `$TMPDIR` или `/tmp`, 002); провал — только если
  подходящего каталога нет нигде.
- Вывод нужен скрипту — машиночитаемый формат и осмысленный код возврата.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять команду диагностики, работающую без цели
  (проверки клиента) и с целью (проверки клиента и цели).
- **FR-002**: Проверки цели MUST включать: определение платформы и её поддержку,
  наличие обязательных утилит, доступность каталога окружения для записи, свободное
  место относительно размера окружения.
- **FR-003**: Проверки клиента MUST включать: корректность конфигурации, установленность
  и совместимость включённых плагинов, наличие пакета выбранного шелла, доступность
  источников плагинов и рантаймов контейнеров.
- **FR-004**: Для цели система MUST сообщать, есть ли пакет шелла и какие плагины
  совместимы именно с её платформой.
- **FR-005**: Диагностика MUST NOT записывать что-либо на цель.
- **FR-006**: Каждая проверка MUST иметь один из исходов — пройдена, предупреждение,
  провал — и для непройденных MUST указывать причину и действие.
- **FR-007**: Код возврата MUST быть ненулевым, если хотя бы одна проверка провалена, и
  нулевым, если есть только предупреждения.
- **FR-008**: Диагностика MUST иметь машиночитаемый формат вывода.
- **FR-009**: При обычном входе отсутствие пакета шелла под платформу цели MUST быть
  видно пользователю без включения отладочного вывода.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Каждая причина, по которой вход на цель завершится ошибкой и которая
  определима заранее, обнаруживается диагностикой до входа.
- **SC-002**: После диагностики цель остаётся в исходном состоянии в 100% случаев.
- **SC-003**: Диагностика цели занимает не больше времени подключения плюс три секунды.
- **SC-004**: По выводу диагностики пользователь устраняет проблему без обращения к
  документации и отладочному режиму.

## Assumptions

- Набор обязательных утилит цели — тот, что зафиксирован в требованиях к хосту.
- Проверки сетевой связности сверх самого подключения — вне рамок.
