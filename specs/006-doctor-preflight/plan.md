# Implementation Plan: Диагностика клиента и цели до входа

**Branch**: `006-doctor-preflight` | **Date**: 2026-10-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/006-doctor-preflight/spec.md`

## Summary

`xxh doctor [цель]` прогоняет проверки клиента (конфиг, плагины, пакет шелла,
источники, рантаймы) и, если задана цель, подключается к ней тем же транспортом, что
вход, и выполняет только чтения: потоковые `detect`, новая подкоманда `probe`
(утилиты, каталог, куда лёг бы вход, свободное место) и `status` из 005 (что уже
лежит). Решения «пройдено/предупреждение/провал» принимаются на клиенте чистыми
функциями по этим ответам и по тому же плану компонентов, что использует вход (005
`plan_components`), — так диагноз не расходится с поведением входа (SC-001).

Поиск пакета шелла начинает различать «пакета нет» и «пакет есть, но без сборки под
эту платформу»; второй случай при обычном входе становится видимым (FR-009):
заметкой, если шелл нашёлся на цели, и отдельной ошибкой класса shell, если нет.

## Technical Context

**Language/Version**: Rust 1.85, edition 2024; POSIX `sh` на цели

**Primary Dependencies**: существующие — новых нет

**Storage**: N/A (ничего не пишется ни на цель, ни на клиент)

**Testing**: unit — оценка проверок по ответу `probe` и плану (утилиты, корень,
место), проверки клиента на временных реестре и каталоге шеллов, рендер и JSON,
различение «нет пакета / нет сборки»; интеграция — SSH (alpine, debian) и бинарь
против контейнера: всё пройдено → вход успешен, цель чиста; недостижимая цель — код
10 и проверки клиента в выводе

**Target Platform**: без изменений

**Project Type**: CLI-инструмент, многокрейтовый workspace

**Performance Goals**: подключение + 3 с (SC-003): три потоковых вызова и один
`command -v`

**Constraints**: ни одной записи на цель (FR-005) — только `upload_stream("sh -s --
…")` и `exec("command -v …")`; контракт хоста не расширяется (`df`, `du`, `zstd` —
желательные)

**Scale/Scope**: `bootstrap.sh` (`probe`), `xxh-core` (`shellpkg::lookup`,
`doctor.rs`, заметки плана), `xxh-cli` (`commands/doctor.rs`, подкоманда, печать
заметок при входе), два интеграционных теста

## Constitution Check

*GATE: конституция v1.5.0. Проверено до Phase 0 и после Phase 1.*

| Принцип | Как соблюдается | Статус |
|---|---|---|
| I. Zero-footprint | Только потоковые вызовы скрипта и `command -v`; поиск корня без `mkdir`; интеграционный тест проверяет чистоту цели и неизменность образа | ✅ |
| II. Статический бинарник | Новых зависимостей нет; FR-009 усиливает правило «явная ошибка вместо частичного окружения» для отсутствующей сборки шелла | ✅ |
| III. Транспорт | Общая фабрика из 005; `xxh-core` не знает семейства | ✅ |
| IV. Плагины | Совместимость включённых плагинов с платформой цели — тем же фильтром, что при входе | ✅ |
| V. Безопасность | Ничего не исполняется на цели, кроме скрипта клиента; в выводе нет секретов (пути к ключам не печатаются) | ✅ |
| VI. Производительность | Без упаковки: адреса и размеры по дереву | ✅ |
| VII. Наблюдаемость | Суть фичи: каждая проверка — исход, причина, действие; `--json`; осмысленный код возврата | ✅ |
| VIII. Тестируемость | Интеграция на реальных sshd и контейнере с проверкой чистоты | ✅ |
| IX. Источники | Доступность `git`/`nix` — предупреждение, без ветвлений по источнику в логике входа | ✅ |
| X–XI | Конфиг читается тем же загрузчиком; ошибка конфига — провал проверки | ✅ |

**Structure Decision**: логика проверок цели — в `xxh-core` (тестируется без
сети), проверки клиента — в `xxh-cli` рядом с загрузкой конфига и реестра.
