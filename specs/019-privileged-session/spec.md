# Feature Specification: Своё окружение после повышения привилегий

**Feature Branch**: `019-privileged-session`

**Created**: 2026-10-01

**Status**: Draft

**Priority**: P2

**Summary**: Стать root или другим пользователем на цели и остаться в своём шелле со своими инструментами

**Input**: User description: "sudo-режим: `xxh host --become root` сохраняет окружение после повышения прав; самая частая боль у подобных инструментов — после `sudo -i` окружение пропадает."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Сессия от имени другого пользователя (Priority: P1)

Пользователь администрирует сервер: ему нужна сессия root (или служебного
пользователя), но со своим шеллом, алиасами и плагинами. Он указывает это при входе и
после штатного запроса на повышение прав получает такую сессию.

**Why this priority**: значительная часть работы на серверах идёт с повышенными
правами; сегодня при переходе окружение теряется, и инструмент перестаёт быть полезным.

**Independent Test**: войти с указанием целевого пользователя; в сессии `id` показывает
его, шелл и плагины — пользовательские; после выхода на цели чисто.

**Acceptance Scenarios**:

1. **Given** у пользователя есть право повышения привилегий на цели, **When** он входит
   с указанием целевого пользователя, **Then** сессия идёт от имени этого пользователя в
   окружении, перенесённом с клиента.
2. **Given** повышение требует пароля, **When** пользователь входит, **Then** пароль
   запрашивается штатным механизмом цели, вводится в терминале и нигде не сохраняется.
3. **Given** сессия завершена, **When** проверяется цель, **Then** артефактов окружения
   нет, файлов, принадлежащих целевому пользователю, в каталоге окружения не осталось.
4. **Given** права повышения нет, **When** пользователь входит, **Then** он получает
   ошибку с причиной, обычная сессия при этом возможна.

---

### User Story 2 - Повышение внутри уже открытой сессии (Priority: P2)

Пользователь уже в сессии и хочет временно стать root, не теряя окружение, а затем
вернуться.

**Why this priority**: частый ход работы, но закрывается первым сценарием через новый
вход.

**Independent Test**: в сессии выполнить команду перехода; окружение сохранилось; выход
возвращает в исходную сессию.

**Acceptance Scenarios**:

1. **Given** открытая сессия, **When** пользователь выполняет предоставленную команду
   перехода, **Then** он получает вложенный шелл целевого пользователя в том же
   окружении, а выход возвращает его обратно.

---

### Edge Cases

- Целевой пользователь не может читать каталог окружения — права на время сессии
  настраиваются минимально достаточным образом, без открытия каталога всем.
- Программы целевого пользователя создают файлы в каталоге окружения — очистка
  исходным пользователем всё равно гарантирована.
- Механизм повышения сбрасывает переменные окружения — окружение восстанавливается.
- Контейнерная цель — повышение выражается штатной возможностью рантайма; запросов
  пароля нет.
- На цели нет средств повышения привилегий — явная ошибка.
- Домашний каталог и собственные конфиги целевого пользователя не изменяются.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Пользователь MUST иметь возможность указать при входе целевого
  пользователя, от имени которого пойдёт сессия.
- **FR-002**: Сессия от имени целевого пользователя MUST использовать шелл,
  конфигурацию и плагины, перенесённые с клиента.
- **FR-003**: Повышение привилегий MUST выполняться только штатным механизмом цели, по
  уже имеющимся у пользователя правам; система MUST NOT требовать root для собственной
  работы.
- **FR-004**: Пароли и иные секреты повышения MUST NOT сохраняться, передаваться в
  аргументах команд или журналироваться.
- **FR-005**: Окружение MUST оставаться в каталоге окружения исходного пользователя;
  в домашний каталог целевого пользователя и системные каталоги MUST NOT записываться
  ничего.
- **FR-006**: Очистка MUST быть гарантирована, включая файлы, созданные целевым
  пользователем в каталоге окружения.
- **FR-007**: Доступ к каталогу окружения для целевого пользователя MUST выдаваться
  минимально достаточный и MUST NOT открывать его остальным пользователям цели.
- **FR-008**: Система MUST предоставлять в сессии способ перейти к другому пользователю
  с сохранением окружения и вернуться.
- **FR-009**: Отказ в повышении привилегий MUST давать понятную ошибку и MUST NOT
  оставлять артефактов.
- **FR-010**: Возможность MUST работать для SSH-хостов и контейнеров.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь получает сессию root со своим окружением одной командой.
- **SC-002**: После выхода на цели нет артефактов, в том числе принадлежащих целевому
  пользователю, в 100% сценариев.
- **SC-003**: Ни один секрет повышения привилегий не обнаруживается в журналах, списке
  процессов и на диске.
- **SC-004**: Домашний каталог целевого пользователя после сессии не отличается от
  состояния до неё.

## Assumptions

- Не противоречит Принципу I: инструмент по-прежнему не требует root; повышение — выбор
  пользователя в рамках его прав.
- Основной механизм — sudo-подобные средства; набор поддерживаемых определяется на этапе
  планирования.
- Для контейнеров уже существует выбор пользователя исполнения (`--user`); эта фича
  распространяет идею на SSH-хосты и добавляет переход внутри сессии.
