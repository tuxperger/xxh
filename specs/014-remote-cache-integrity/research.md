# Research: Целостность сохранённого окружения на цели

## R1. Средства проверки на цели

- **Decision**: `find` + `sha256sum` (+ `sed`), если присутствуют; иначе ответ
  `unverifiable <причина>`. Обе утилиты есть в BusyBox и coreutils, но в контракт
  хоста не входят — поэтому только «если есть» (FR-007), а их отсутствие отключает
  переиспользование, а не проверку молча (FR-006).
- **Alternatives**: доставлять свою утилиту хеширования — статическая сборка под
  каждую архитектуру цели и её собственная проверка; `cksum` (CRC) — не стойкий;
  возвращать дерево на клиент — трафик всего окружения на каждом входе.

## R2. Что сравнивается

- **Decision**: описание компонента — множества каталогов, исполняемых файлов,
  «прочих» объектов (симлинки, FIFO и т. п.) и отображение «файл → SHA-256»; пути
  относительно корня компонента в форме `./…`. Ожидаемое описание клиент строит
  из своего экземпляра: дерево каталога (симлинки разыменованы — так их
  упаковывает tar 023) или записи архива сгенерированного компонента. Сравнение —
  на клиенте, по множествам: формат вывода цели и порядок сортировки неважны.
- **Rationale**: устойчиво к различиям `find`/`sort` между BusyBox и GNU; лишний
  файл, симлинк или смена признака исполняемости обнаруживаются.

## R3. Когда и что делать

- **Decision**: после `reconcile` — `verify` для нужных сессии компонентов; затем
  `list-cache` и доставка отсутствующих + несовпавших (несовпавшие сначала
  `discard`); после доставки — `verify` доставленных; несовпадение после доставки —
  ошибка класса компонента (shell/plugin; config → shell). Права корня — из того
  же `verify` (до `chmod 700` в `list-cache`).
- **Rationale**: ничего из компонента не подключается до прохождения проверки
  (prelude собирается после).

## R4. Код выхода `recv`

- **Decision**: `upload_stream(recv …)` с ненулевым кодом — ошибка класса
  компонента с текстом stderr (US2 сценарий 2).
