# Feature Specification: Программы-плагины из Nix flake

**Feature Branch**: `003-flake-plugin-source`

**Created**: 2026-10-01

**Status**: Implemented

**Priority**: P1

**Summary**: Подключить как плагин программу или готовый пакет-плагин из любого flake одной командой; на цель без Nix едет статический артефакт

**Input**: User description: "Загрузка программ-плагинов из Nix flake. Пользователь командой `xxh plugin add flake:<flake-ссылка>#<выход>` подключает как плагин программу или готовый пакет-плагин, который экспортирует произвольный flake (GitHub/GitLab-репозиторий, git-URL, локальный каталог с flake.nix), а не только атрибут из nixpkgs. Сборка идёт на клиенте, на цель (SSH-хост или контейнер без Nix и без root) доставляется самодостаточный статический артефакт; ревизия flake фиксируется при установке, чтобы окружение было воспроизводимым, и обновляется только по явной команде. Если выход flake уже содержит манифест плагина — он используется как полноценный плагин (env, хуки, зависимости); если это просто программа с bin/ — она оборачивается в плагин автоматически. Отсутствие Nix на клиенте отключает только этот источник. Продолжение опционального Nix-источника из фичи 001 (nixpkgs:<attr>)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Программа из чужого flake в своём окружении (Priority: P1)

Пользователь нашёл инструмент, которого нет в nixpkgs или который нужен в более свежей
версии, — он опубликован как flake в репозитории автора. Пользователь одной командой
добавляет этот выход flake как плагин, включает его и при следующем входе на любой хост
или в контейнер получает программу в `PATH` — на машине, где нет ни Nix, ни прав root.

**Why this priority**: это и есть суть фичи. Сегодня программа доступна только если она
есть в зафиксированном снимке nixpkgs; всё остальное приходится оборачивать в плагин
вручную.

**Independent Test**: добавить выход flake, дающий статически собранную программу,
включить плагин, войти на минимальный хост без Nix, запустить программу, выйти и
убедиться, что на хосте ничего не осталось.

**Acceptance Scenarios**:

1. **Given** клиент с Nix и flake, чей выход — статически собранная программа,
   **When** пользователь выполняет `xxh plugin add flake:<ссылка>#<выход>` и включает
   плагин, **Then** при входе на хост без Nix программа запускается из `PATH`.
2. **Given** установленный таким образом плагин, **When** пользователь выходит из
   сессии без `--keep`, **Then** на цели не остаётся ни одного артефакта плагина.
3. **Given** ссылка на flake без указания выхода, **When** пользователь добавляет
   плагин, **Then** используется выход по умолчанию этого flake.
4. **Given** локальный каталог с flake, **When** пользователь добавляет плагин по пути
   к нему, **Then** плагин устанавливается так же, как из удалённого репозитория.
5. **Given** тот же плагин уже доставлен на хост в сохранённое (`--keep`) окружение,
   **When** пользователь входит повторно, **Then** плагин повторно не передаётся.

---

### User Story 2 - Воспроизводимость: зафиксированная ревизия (Priority: P1)

Пользователь добавил плагин из ветки репозитория. Через месяц автор выпустил несовместимое
изменение. Окружение пользователя не меняется само собой: плагин остаётся тем же, пока
пользователь явно не попросит обновить. В списке плагинов видно, откуда плагин взят и на
какой ревизии он зафиксирован.

**Why this priority**: без фиксации окружение, которое пользователь несёт на рабочие
хосты, меняется непредсказуемо — это нарушает принцип воспроизводимости и делает
источник непригодным для повседневной работы.

**Independent Test**: установить плагин из локального flake-репозитория, сделать в
репозитории новый коммит, убедиться, что сведения о плагине и его содержимое не
изменились; выполнить обновление и убедиться, что зафиксирована новая ревизия.

**Acceptance Scenarios**:

1. **Given** плагин установлен из flake по плавающей ссылке (ветка), **When** в
   источнике появляются новые коммиты, **Then** установленный плагин и то, что едет на
   хосты, не меняются.
2. **Given** установленный плагин, **When** пользователь выполняет
   `xxh plugin update <имя>`, **Then** ссылка разрешается заново, фиксируется новая
   ревизия и сообщается, с какой на какую ревизию обновлён плагин.
3. **Given** установленный плагин, **When** пользователь выполняет `xxh plugin list`,
   **Then** для плагина показаны исходная ссылка и зафиксированная ревизия.
4. **Given** плагин добавлен из локального каталога с незакоммиченными изменениями,
   **When** установка завершается, **Then** пользователь предупреждён, что источник не
   имеет фиксированной ревизии и установка невоспроизводима.

---

### User Story 3 - Готовый плагин, собранный flake (Priority: P2)

Автор плагина описывает его целиком в flake: манифест, переменные окружения, хуки
жизненного цикла, зависимости от других плагинов и собранные программы. Пользователь
добавляет такой выход — и получает полноценный плагин, а не просто программу в `PATH`.

**Why this priority**: открывает flake как способ распространения плагинов и шеллов
наравне с git-репозиторием, но с воспроизводимой сборкой. Не блокирует сценарий
«просто программа».

**Independent Test**: добавить выход flake, содержащий манифест плагина с переменной
окружения и зависимостью; убедиться, что имя, версия, зависимости взяты из манифеста, а
переменная видна в сессии.

**Acceptance Scenarios**:

1. **Given** выход flake содержит манифест плагина в корне, **When** пользователь
   добавляет его, **Then** плагин устанавливается под именем и версией из манифеста, с
   его хуками, зависимостями и ограничениями по платформам.
2. **Given** манифест в выходе несовместим с клиентом или некорректен, **When**
   пользователь добавляет плагин, **Then** установка отклоняется с ошибкой класса
   «плагин», указывающей причину; ничего не устанавливается.
3. **Given** выход flake содержит и манифест, и исполняемые файлы, **When** плагин
   устанавливается, **Then** исполняемые файлы проходят ту же проверку
   самодостаточности, что и у программы без манифеста.

---

### User Story 4 - Понятный отказ, когда артефакт не годится для цели (Priority: P2)

Пользователь добавляет выход flake, который собран с динамическими зависимостями, или
входит на хост другой архитектуры, или работает на клиенте без Nix. В каждом случае он
получает внятное сообщение о том, что именно не так и что сделать, — а не программу,
которая падает на хосте с «not found».

**Why this priority**: большинство flake по умолчанию дают динамически слинкованные
программы; без этой проверки первая же попытка пользователя закончится непонятной
ошибкой на удалённой машине.

**Independent Test**: добавить выход с динамически слинкованной программой — установка
отклонена с объяснением; войти на хост архитектуры, отличной от архитектуры сборки, —
плагин пропущен с предупреждением, сессия работает.

**Acceptance Scenarios**:

1. **Given** выход flake с программой, требующей динамических библиотек, **When**
   пользователь добавляет плагин, **Then** установка отклоняется до записи в реестр, с
   перечислением неподходящих файлов и подсказкой, какой выход нужен.
2. **Given** плагин собран для одной архитектуры, **When** пользователь входит на хост
   другой архитектуры, **Then** плагин на этот хост не доставляется, пользователь видит
   предупреждение, остальное окружение работает.
3. **Given** клиент без Nix (или без поддержки flake), **When** пользователь выполняет
   `xxh plugin add flake:…`, **Then** он получает сообщение, что источник недоступен и
   почему; плагины из других источников и вход на хосты работают как прежде.
4. **Given** сборка выхода flake завершается ошибкой, **When** пользователь добавляет
   плагин, **Then** ошибка относится к классу «плагин», содержит конец вывода сборки и
   не оставляет частично установленного плагина.

---

### Edge Cases

- Выход flake не содержит ни манифеста плагина, ни исполняемых файлов — установка
  отклоняется с объяснением, что именно ожидается в выходе.
- Указанного выхода в flake нет, либо flake не предоставляет выходов для платформы
  клиента — ошибка называет ссылку и отсутствующий выход.
- Два разных flake дают плагины с одинаковым именем — второй не затирает первый молча:
  пользователь получает сообщение о конфликте и способ задать другое имя.
- Источник недоступен по сети при установке или обновлении — ошибка класса «плагин»,
  ранее установленный плагин остаётся рабочим.
- Flake объявляет собственные настройки сборщика (дополнительные источники готовых
  сборок и т. п.) — они не принимаются без ведома пользователя.
- Программа из выхода нуждается в данных времени исполнения (описания терминалов,
  корневые сертификаты) — на хосте без Nix она должна находить их в доставленном пакете.
- Ссылка на flake содержит учётные данные (токен в URL) — они не попадают в вывод
  команд, сообщения об ошибках и журналы.
- Повторное добавление того же выхода той же ревизии — не выполняет повторную сборку и
  не меняет состояние.
- Аргумент `xxh plugin add` формально подходит и под flake-ссылку, и под уже
  существующие формы (git-URL, локальный путь, `nixpkgs:`) — существующие формы
  продолжают разбираться как раньше; flake выбирается только по явному префиксу.

## Requirements *(mandatory)*

### Functional Requirements

**Адресация и установка**

- **FR-001**: Пользователь MUST иметь возможность добавить плагин, указав flake и его
  выход в форме `flake:<ссылка>#<выход>`; `<ссылка>` — любая форма, которой адресуются
  flake (репозиторий на хостинге, git-URL, локальный каталог).
- **FR-002**: При отсутствии `#<выход>` система MUST использовать выход по умолчанию
  указанного flake.
- **FR-003**: Источник flake MUST выбираться только по явному префиксу `flake:`;
  разбор остальных форм аргумента (git-URL, локальный путь, `nixpkgs:<attr>`) MUST
  остаться неизменным.
- **FR-004**: Плагин из flake MUST управляться теми же командами, что и плагины из
  других источников: включение, отключение, удаление, обновление, список.

**Форма выхода**

- **FR-005**: Если в корне собранного выхода есть манифест плагина, система MUST
  установить выход как готовый плагин, взяв имя, версию, зависимости, хуки и
  ограничения по платформам из манифеста, и MUST применить к манифесту те же проверки
  совместимости, что и для плагинов из других источников.
- **FR-006**: Если манифеста нет, но выход содержит исполняемые программы, система MUST
  автоматически оформить его как плагин, делающий эти программы доступными в `PATH`
  сессии.
- **FR-007**: Если выход не содержит ни манифеста, ни исполняемых программ, установка
  MUST быть отклонена с сообщением о том, что ожидается в выходе.
- **FR-008**: Автоматически оформленный плагин MUST получать имя, детерминированно
  выводимое из ссылки и выхода; пользователь MUST иметь возможность задать имя явно.
- **FR-009**: Установка плагина, чьё имя совпадает с уже установленным плагином из
  другого источника, MUST быть отклонена с сообщением о конфликте и о том, как его
  разрешить; повторная установка из того же источника MUST обновлять плагин на месте.

**Пригодность для цели**

- **FR-010**: Каждый исполняемый файл в устанавливаемом плагине MUST быть проверен на
  самодостаточность (не требует динамического загрузчика и библиотек, которых нет на
  цели); при нарушении установка MUST быть отклонена до записи в реестр, с перечнем
  файлов и подсказкой.
- **FR-011**: Автоматически оформленный плагин MUST включать данные времени исполнения,
  которые программа не может нести в себе (описания терминалов, корневые сертификаты),
  в том же объёме, что и плагины из nixpkgs-источника.
- **FR-012**: Плагин MUST быть помечен платформой, для которой он собран, и MUST
  доставляться только на цели этой платформы; на прочих целях он пропускается с
  предупреждением, не прерывая сессию.
- **FR-013**: На цели MUST NOT требоваться Nix, права root или доступ в сеть; всё
  необходимое доставляется по уже установленному соединению и подчиняется общим
  правилам очистки и кеширования.

**Воспроизводимость**

- **FR-014**: При установке система MUST зафиксировать точную ревизию flake и сохранить
  её вместе с исходной ссылкой.
- **FR-015**: Все действия с установленным плагином, кроме явного обновления, MUST
  использовать зафиксированную ревизию; появление новых ревизий в источнике MUST NOT
  менять установленный плагин.
- **FR-016**: `xxh plugin update <имя>` MUST заново разрешить исходную ссылку,
  зафиксировать новую ревизию и сообщить прежнюю и новую ревизии; если ревизия не
  изменилась, это MUST быть сообщено без пересборки.
- **FR-017**: `xxh plugin list` MUST показывать для плагина из flake исходную ссылку и
  зафиксированную ревизию.
- **FR-018**: Если у источника нет фиксируемой ревизии (локальный каталог с
  незафиксированными изменениями), установка MUST завершиться успешно с явным
  предупреждением о невоспроизводимости.
- **FR-019**: Повторная установка той же ревизии того же выхода MUST NOT вызывать
  повторную сборку.

**Отказоустойчивость и безопасность**

- **FR-020**: Отсутствие на клиенте Nix или поддержки flake MUST отключать только этот
  источник, с сообщением о причине; остальные источники плагинов и все прочие функции
  MUST работать без изменений.
- **FR-021**: Все сбои источника (недоступная ссылка, отсутствующий выход, ошибка
  сборки, неподходящий артефакт) MUST относиться к классу ошибок «плагин» и быть
  отличимы от ошибок транспорта, шелла и конфигурации.
- **FR-022**: Неудачная установка или обновление MUST NOT оставлять частично
  установленный плагин и MUST NOT повреждать ранее установленную версию.
- **FR-023**: Настройки, объявленные самим flake и влияющие на доверие клиента
  (дополнительные источники готовых сборок, ключи и т. п.), MUST NOT приниматься
  автоматически.
- **FR-024**: Учётные данные, встроенные в ссылку, MUST NOT появляться в выводе команд,
  сообщениях об ошибках и журналах на любом уровне детализации.
- **FR-025**: Сообщение об ошибке сборки MUST содержать достаточно вывода сборщика,
  чтобы пользователь понял причину, без необходимости повторять сборку вручную.

### Key Entities

- **Ссылка на flake**: то, что ввёл пользователь, — адрес flake и имя выхода. Может быть
  плавающей (ветка) или точной (ревизия).
- **Зафиксированная ревизия**: точная, неизменяемая версия flake, выбранная при
  установке или обновлении; определяет содержимое плагина.
- **Выход flake**: результат сборки; либо готовый плагин (с манифестом), либо набор
  программ.
- **Плагин из flake**: установленный плагин, у которого записаны исходная ссылка,
  зафиксированная ревизия и платформа сборки.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь делает программу из стороннего flake доступной в своём
  окружении на удалённом хосте не более чем за две команды (добавить, включить) и без
  ручного создания манифеста.
- **SC-002**: Программа, установленная из flake, запускается на минимальном хосте без
  Nix и без root на обеих обязательных осях совместимости (glibc и musl/BusyBox).
- **SC-003**: После выхода из сессии на цели не остаётся ни одного артефакта плагина —
  в 100% сценариев, включая аварийное завершение.
- **SC-004**: Содержимое установленного плагина не меняется между сессиями, пока
  пользователь явно не обновит его, независимо от изменений в источнике.
- **SC-005**: Неподходящий для цели артефакт отклоняется на клиенте в 100% случаев —
  пользователь узнаёт о проблеме при установке, а не при запуске программы на хосте.
- **SC-006**: На клиенте без Nix все существующие сценарии (вход, плагины из git и
  локального пути) работают без изменений; обращение к flake-источнику даёт сообщение
  с причиной и действием.
- **SC-007**: Повторная установка неизменившегося выхода завершается за секунды, без
  сборки.
- **SC-008**: По сообщению и коду завершения пользователь отличает сбой
  flake-источника от ошибок соединения, шелла и конфигурации без обращения к
  документации.

## Assumptions

- Фича расширяет опциональный Nix-источник фичи 001 (001 §FR-033–040) и подчиняется тем
  же принципам: Nix нужен только на клиенте и только для таких плагинов; источник
  включается той же опцией сборки, что и `nixpkgs:<attr>`.
- Ответственность за статическую сборку — на flake: система проверяет результат и
  отклоняет неподходящий, но не пытается пересобрать чужой пакет статически.
  Автоматическая статическая пересборка произвольного выхода — вне рамок.
- Плагин собирается для платформы клиента. Сборка под архитектуру цели, отличную от
  клиента (кросс-сборка по требованию), — вне рамок этой фичи; пользователь может
  указать выход flake, уже собранный под нужную платформу.
- Целевые платформы — Linux; для прочих источник сообщает о неподдерживаемой цели, как
  и nixpkgs-источник.
- Сборка исполняет код чужого flake на клиенте в изоляции сборщика; добавляя плагин,
  пользователь явно выражает доверие источнику — как и при установке плагина из git.
- Декларативное перечисление источников плагинов в конфигурации (включая Nix-модули) и
  общий lock-файл плагинов — отдельные фичи; здесь зафиксированная ревизия хранится в
  локальном реестре плагинов.
- Перенос программ с динамическими зависимостями вместе с их замыканием — вне рамок.
- Принцип IX конституции описывает Nix-источник словами «сборка из nixpkgs»; flake —
  обобщение того же механизма без ослабления его правил. Если потребуется, формулировка
  уточняется отдельной поправкой к конституции.
